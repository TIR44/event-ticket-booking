# ADR-006: оркестрация покупки в Booking и доставка через outbox

- **Статус:** принято для учебного проекта
- **Дата:** 2026-09-20

## Контекст

У темы №6 есть ограниченное место, резерв на 10 минут и внешний платёж с неопределённым результатом. Поздний успех требует возврата. По [ADR-002](ADR-002-domain-ownership.md) Booking, Payments и Notifications владеют отдельными БД, оставаясь модулями одного backend-артефакта. Общая транзакция с платёжным провайдером невозможна.

Нужно сохранять принятую работу при падении процесса, предотвращать повторный денежный эффект и оставлять UI восстанавливаемым. Критерии: Q-01–Q-04 из [сценариев качества](../architecture-drivers.md). Ограничения нагрузки и гарантии провайдера пока являются [допущениями](../assumptions.md), а не измеренными фактами.

## Рассмотренные варианты

| Вариант | Польза | Цена и причина выбора |
|---|---|---|
| Синхронная цепочка Booking → Payments → провайдер → уведомление | Прямой ход вызова | Долгое ожидание, зависимость покупки от уведомления, неизвестность после timeout. Даже такая цепочка требует сохранённого восстановления; отклонена |
| Оркестрация Booking, локальные outbox/inbox и worker | Видно решение о покупке и компенсации; данные каждого владельца фиксируются локально | Нужно реализовать аренду, повторы, дедупликацию и наблюдаемость; выбран для одного артефакта |
| Хореография с внешним брокером | Независимые потребители и fan-out | Сценарий и компенсация распределены, нужна отдельная инфраструктура; требуемой независимости команд/релизов нет. Не решает атомарность внешнего платежа; отклонена |
| Очередь в памяти процесса | Минимальная первоначальная настройка | Теряет принятую работу при рестарте, не выполняет Q-04; отклонена |

## Решение

Booking владеет долговечным процессом покупки и решает, выпустить билет либо потребовать полный возврат. Payments владеет единственной попыткой, адаптером провайдера и денежной сверкой. Notifications доставляет подтверждение независимо от исхода покупки.

Ответ запроса оплаты — HTTP 202 после commit намерения и outbox Booking. Worker доставляет команду в публичный порт Payments. Получатель сохраняет inbox и изменение своей БД одной транзакцией и только затем подтверждает приём. Денежный факт и обратный outbox Payments также фиксируются вместе. Booking применяет успех с новой проверкой срока; событие не подтверждает просроченную покупку.

Одна экономическая операция узнаётся по попытке/reference, а не только по transport message ID. Внешние вызовы идут вне DB-транзакций. Нет обещания exactly-once для всей цепочки: отсутствие второго списания зависит от идемпотентности и lookup провайдера по A-05. При истечении этих гарантий неопределённость разбирается без слепого повторного create/refund.

Подробные последовательности, контракты, ключи, сроки хранения и retry — в [модели взаимодействия](../interaction-model.md). Правила покупки остаются в [жизненном цикле](../booking-lifecycle.md), а не копируются в frontend или Payments.

## Последствия

Принятая работа восстанавливается после рестарта, ошибка уведомления изолирована, решение о месте остаётся локально атомарным. HTTP быстро сообщает приём, UI продолжает чтение статуса.

Цена: согласованность между модулями наступает позже; UI показывает промежуточные состояния. Worker, карантин и мониторинг становятся частью обязательной реализации. Хранение inbox/ключей требует будущей политики архивирования. Общий PostgreSQL остаётся общей точкой отказа. Outbox не устраняет зависимость от возможностей внешнего провайдера.

## Проверка и пересмотр

Будущая проверка останавливает процесс после commit отправителя и после commit получателя до ACK, теряет ответ провайдера после эффекта, повторяет команды с разными ключами. Ожидается одна попытка, один билет либо один возврат и восстановление незавершённой работы. Это требования к реализации; приложение ещё не написано.

Рассмотреть брокер при независимых релизах потребителей, потребности в нескольких подписчиках/длительном replay либо измеримом влиянии очередей на DB/API, которое не устраняется настройкой worker. Выбор брокера должен включать стоимость эксплуатации и миграции, сохранение бизнес-ключей и совместимость схем. Workflow engine рассматривается при существенно более длинном процессе с несколькими компенсациями; один резерв/платёж его сейчас не требует.

# ADR-007: один кластер с синхронными репликами, идентификаторы покупки несут виртуальный шард

- **Статус:** принято для учебного проекта
- **Дата:** 2026-10-27
- **Драйверы:** Q-01, Q-02, Q-04

## Контекст

Быстрее всего растёт Booking: места сеансов, резервы, заказы, намерения, билеты и их ключи — около 47 млн строк и 25–35 ГБ в год по A-08. В пик A-03 это до 50 команд изменения в секунду, то есть порядка 300–500 записей строк. [Разбор по лестнице масштабирования](../data-scaling.md#шаг-2-шардировать-или-нет) показал, что один узел PostgreSQL держит это с запасом, а шарды сегодня добавили бы только издержки.

Там же нашлись две проблемы, которые от шардов не зависят. Первая: `orderId` — случайный UUID, а самое частое чтение системы — опрос статуса заказа каждые 4–6 секунд. При будущем шардировании по `sessionId` этот запрос ушёл бы во все шарды. Вторая: все четыре БД жили на одном экземпляре без копий, и [тактики надёжности](../reliability.md#тип-сбоя-и-первая-тактика) не имели ответа на потерю его диска.

| Вариант | Польза | Цена и решение |
|---|---|---|
| Шардировать Booking сейчас по `sessionId` | Готовность к росту записи | Отчёты организатора обходят все шарды, миграции и копии умножаются на число узлов, нагрузки для этого нет. Отклонено |
| Шардировать по `buyerId` | Все заказы покупателя в одном месте | Два покупателя одного места попадают в разные шарды, исключительность требует распределённой транзакции. Отклонено |
| Одна база, случайные UUID, без реплик | Минимум работы сегодня | Потеря диска теряет оплаченные покупки; переход к шардам потом требует миграции всех идентификаторов. Отклонено |
| Справочник `orderId → виртуальный шард` вместо номера в идентификаторе | Формат UUID не меняется | Ещё одна таблица на пути самого частого чтения, которую при шардах надо реплицировать и кешировать; ~5 млн строк в год. Отклонено: номер в идентификаторе бесплатен при чтении |
| Синхронный commit только для Booking и Payments | Каталог и уведомления пишут быстрее и переживают пустой кворум | При отказе лидера мог бы пропасть уже подтверждённый асинхронный commit: публикация, которую организатор видел успешной, или отметка о доставке. Выигрыш при 50 командах в секунду мал, а две настройки сложнее одной. Отклонено |
| Отдельный кластер для Booking и Payments | Пустой кворум или восстановление строгих баз не задевает каталог и уведомления | Два кластера, две схемы переключения и резервных копий при одной команде и одном артефакте. Отложено: см. условия пересмотра |
| Один кластер, синхронный кворум на весь кластер, идентификаторы с виртуальным шардом | Ноль потерь после commit, будущие шарды без миграции идентификаторов | Больше узлов, задержка commit на сетевой круг, остановка записи при пустом кворуме. Выбрано |

## Решение

Четыре БД остаются **в одном кластере PostgreSQL** без шардов. Шарды возвращаются в повестку по числу: пик устойчиво выше 500 команд изменения в секунду после вертикального роста или горячие секции `booking_db` больше 500 ГБ.

Кластер — **лидер и две реплики с синхронным кворумом «любая одна из двух»**. Кворум выставляет Patroni в режиме `synchronous_mode: quorum`, `synchronous_node_count: 1`, `synchronous_mode_strict: true`, с etcd как хранилищем консенсуса; `synchronous_commit = on` задан для кластера, приложение его не меняет. Все базы пишут и читают только лидера. Для транзакций команд `statement_timeout` не задаётся, потому что он прерывает и ожидание реплики на COMMIT; бюджет держит `lock_timeout`. Повтор по ключу подтверждает сохранённый ответ пишущей транзакцией. Отказ лидера закрывается автоматическим переключением, цель до 60 секунд. Дополнительно — базовые копии и непрерывный архив журнала: RPO до минуты, RTO восстановления до 4 часов; после восстановления продажи открываются только после сверки по реестру операций провайдера, а найденные оплаты возвращаются.

`orderId`, `reservationId` и `ticketId` генерируются как **UUID версии 8**: старшие 10 бит поля `custom_a` несут номер виртуального шарда, остальные 38 — миллисекунды от собственной эпохи 2026-01-01 для локальности индекса и архива по дате, затем 74 случайных бита. 38 бит хватает примерно на 8,7 года; после этого счётчик идёт по кругу — уникальность держат случайные биты, а локальность индекса ненадолго теряется. Номер назначается сеансу при импорте его снимка и хранится в нём: обычный сеанс получает `hash(sessionId) mod 960` по стабильной хеш-функции, не зависящей от языка; горячий — свободный номер из резерва 960..1023. Формат `uuid` в контрактах не меняется, а описание `orderId` в OpenAPI запрещает клиентам разбирать его структуру.

## Последствия

**Что выигрываем.** Сегодня — простота одной базы: резерв, заказ и билет остаются одной локальной транзакцией, отчёты не обходят узлы, а подтверждённые данные всех четырёх баз переживают потерю любого одного узла. Завтра — шардирование без миграции идентификаторов: схема мест, резерв и статус заказа попадают в один шард, переезд идёт целыми виртуальными шардами, горячий сеанс уезжает на свой узел, не ломая маршрут по `orderId`.

**Чем платим.**
- Три узла PostgreSQL и три узла etcd — или управляемый PostgreSQL с теми же гарантиями; задержка каждого commit на сетевой круг до реплики.
- Пустой кворум останавливает новую запись во всех четырёх базах, включая каталог и уведомления, — тот же главный компромисс: корректность важнее доступности подтверждения.
- Одновременный отказ лидера и одной реплики автоматически не закрывается: переключение ручное.
- Одно переключение лидера съедает около 10% недельного бюджета SLI-1.
- Идентификатор перестаёт быть непрозрачным. Генерация требует номер шарда сеанса в момент создания — в команде резервирования он известен из снимка.
- 1024 виртуальных шарда — предел числа физических шардов без перевыпуска идентификаторов.
- Переключение лидера требует синхронизированных часов узлов: срок резерва проверяется по времени БД.

## Условия пересмотра

- Пик или горячие секции `booking_db` превысили порог — включить шардирование по `sessionId` через заложенные виртуальные шарды.
- Пустой кворум случается чаще раза в квартал — третья реплика в кворуме.
- Переключения лидера случаются чаще раза в месяц — разбор их причин и настройка таймаутов обнаружения отказа; число реплик здесь не помогает.
- Пустой кворум или восстановление из архива задели каталог и уведомления заметнее, чем их общая настройка экономит, — отдельный кластер для Booking и Payments.
- Чтение каталога стало нагрузкой на лидера — сначала кеш в приложении, затем анонимные GET каталога на реплику с порогом отставания и уменьшением `s-maxage` на это отставание.
- Появилось требование пережить потерю площадки — начинать с модели согласованности между регионами, а не с добавления реплик.

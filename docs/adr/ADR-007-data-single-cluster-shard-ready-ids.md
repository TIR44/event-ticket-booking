# ADR-007: один кластер с синхронными репликами, идентификаторы покупки несут виртуальный шард

- **Статус:** принято для учебного проекта
- **Дата:** 2026-10-27
- **Драйверы:** Q-01, Q-02, Q-04

## Контекст

Растёт только Booking: места сеансов, резервы, заказы, билеты и их ключи — около 55 млн строк и 30–40 ГБ в год по A-08, в пик A-03 порядка 300–500 записей в секунду. [Разбор по лестнице масштабирования](../data-scaling.md#шаг-2-шардировать-или-нет) показал, что один узел PostgreSQL держит это с запасом, а шарды сегодня добавили бы только издержки.

Там же нашлись две проблемы, которые от шардов не зависят. Первая: `orderId` — случайный UUID, а самое частое чтение системы — опрос статуса заказа каждые 4–6 секунд. При будущем шардировании по `sessionId` этот запрос ушёл бы во все шарды. Вторая: все четыре БД живут на одном экземпляре без копий, и [тактики надёжности](../reliability.md#тип-сбоя-и-первая-тактика) не имели ответа на потерю его диска.

Рассмотренные варианты:

| Вариант | Польза | Цена и решение |
|---|---|---|
| Шардировать Booking сейчас по `sessionId` | Готовность к росту записи | Отчёты организатора обходят все шарды, миграции и копии умножаются на число узлов, нагрузки для этого нет. Отклонено |
| Шардировать по `buyerId` | Все заказы покупателя в одном месте | Два покупателя одного места попадают в разные шарды, исключительность требует распределённой транзакции. Отклонено |
| Одна база, случайные UUID, без реплик | Минимум работы сегодня | Потеря диска теряет оплаченные покупки; переход к шардам потом требует миграции всех идентификаторов. Отклонено |
| Один кластер, синхронные реплики, идентификаторы с виртуальным шардом | Ноль потерь после commit, будущие шарды без миграции идентификаторов | Три узла, задержка commit на сетевой круг, остановка записи при потере обеих реплик. Выбрано |

## Решение

Четыре БД остаются **в одном кластере PostgreSQL** без шардов. Шарды возвращаются в повестку по числу: пиковая запись устойчиво выше 500 изменений в секунду после вертикального роста или горячие данные `booking_db` больше 500 ГБ.

Кластер — **лидер и две реплики с синхронным кворумом «любая одна из двух»**. Booking, Payments и Notifications пишут и читают только лидера; чтение публичного каталога может идти с реплики с отставанием до 5 секунд. Отказ лидера закрывается автоматическим переключением, цель — до 60 секунд. Дополнительно — базовые копии и непрерывный архив журнала транзакций для восстановления после логической ошибки.

`orderId`, `reservationId` и `ticketId` генерируются как **UUID версии 8**, где 10 бит несут `hash(sessionId) mod 1024` — номер виртуального шарда. Формат `uuid` в контрактах не меняется. Будущая карта «виртуальный шард → узел» живёт в клиентской библиотеке backend-артефакта и допускает исключение «горячий сеанс → выделенный узел». Сегодня все 1024 виртуальных шарда отображаются на один кластер.

## Последствия

**Что выигрываем.** Сегодня — простота одной базы: резерв, заказ и билет остаются одной локальной транзакцией, отчёты не обходят узлы, а подтверждённые покупка и деньги переживают потерю любого одного узла. Завтра — шардирование без миграции идентификаторов: схема мест, резерв и статус заказа попадают в один шард, переезд идёт целыми виртуальными шардами.

**Чем платим.** Три узла вместо одного и задержка каждого commit на сетевой круг до реплики. Потеря обеих реплик останавливает запись Booking и Payments — это тот же главный компромисс: корректность важнее доступности подтверждения. Репликация общая на кластер, поэтому дешёвый каталог получает ту же гарантию, что и деньги. Идентификатор перестаёт быть непрозрачным: клиентам и интеграциям прямо запрещено разбирать его структуру. Генерация требует `sessionId` в момент создания — в команде резервирования он есть всегда. Число 1024 зафиксировано на годы; дальше понадобится пересчёт. Переключение лидера требует синхронизированных часов узлов: срок резерва проверяется по времени БД.

## Условия пересмотра

- Пиковая запись или объём `booking_db` превысили порог выше — включить шардирование по `sessionId` через уже заложенные виртуальные шарды.
- Потеря обеих реплик случается чаще, чем допускает бюджет SLI-1, — добавить третью реплику в кворум.
- Появилось требование пережить потерю площадки — начинать с модели согласованности между регионами, а не с добавления реплик.

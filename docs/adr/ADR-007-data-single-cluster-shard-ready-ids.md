# ADR-007: один кластер с синхронными репликами, идентификаторы покупки несут виртуальный шард

- **Статус:** принято для учебного проекта
- **Дата:** 2026-10-27
- **Драйверы:** Q-01, Q-02, Q-04

## Контекст

Быстрее всего растёт Booking: места сеансов, резервы, заказы, намерения, билеты и их ключи — около 58 млн строк и 30–40 ГБ в год по A-08. В пик A-03 это до 50 команд изменения в секунду, то есть порядка 300–500 записей строк. [Разбор по лестнице масштабирования](../data-scaling.md#шаг-2-шардировать-или-нет) показал, что один узел PostgreSQL держит это с запасом, а шарды сегодня добавили бы только издержки.

Там же нашлись две проблемы, которые от шардов не зависят. Первая: `orderId` — случайный UUID, а самое частое чтение системы — опрос статуса заказа каждые 4–6 секунд. При будущем шардировании по `sessionId` этот запрос ушёл бы во все шарды. Вторая: все четыре БД жили на одном экземпляре без копий, и [тактики надёжности](../reliability.md#тип-сбоя-и-первая-тактика) не имели ответа на потерю его диска.

| Вариант | Польза | Цена и решение |
|---|---|---|
| Шардировать Booking сейчас по `sessionId` | Готовность к росту записи | Отчёты организатора обходят все шарды, миграции и копии умножаются на число узлов, нагрузки для этого нет. Отклонено |
| Шардировать по `buyerId` | Все заказы покупателя в одном месте | Два покупателя одного места попадают в разные шарды, исключительность требует распределённой транзакции. Отклонено |
| Одна база, случайные UUID, без реплик | Минимум работы сегодня | Потеря диска теряет оплаченные покупки; переход к шардам потом требует миграции всех идентификаторов. Отклонено |
| Синхронный commit только для Booking и Payments | Каталог и уведомления пишут быстрее и переживают пустой кворум | Потерянный commit получателя рвёт доставку через outbox без повтора: уведомление теряется, версия каталога расходится с Booking. Отклонено |
| Один кластер, синхронный кворум на весь кластер, идентификаторы с виртуальным шардом | Ноль потерь после commit, будущие шарды без миграции идентификаторов | Больше узлов, задержка commit на сетевой круг, остановка записи при пустом кворуме. Выбрано |

## Решение

Четыре БД остаются **в одном кластере PostgreSQL** без шардов. Шарды возвращаются в повестку по числу: пик устойчиво выше 500 команд изменения в секунду после вертикального роста или горячие секции `booking_db` больше 500 ГБ.

Кластер — **лидер и две реплики с синхронным кворумом «любая одна из двух» на весь кластер**: `synchronous_commit = on`, без переопределения базой или ролью. Все базы пишут и читают только лидера. Бюджет запроса ограничивает ожидание блокировки, но не COMMIT: на него не действует `statement_timeout`, и драйвер не отправляет отмену. Повтор по ключу подтверждает сохранённый ответ пишущей транзакцией. Отказ лидера закрывается автоматическим переключением — Patroni с etcd в режиме `synchronous_mode: quorum` и `synchronous_mode_strict: true`, цель до 60 секунд. Дополнительно — базовые копии и непрерывный архив журнала; после восстановления из архива продажи затронутых сеансов открываются только после сверки по реестру операций провайдера.

`orderId`, `reservationId` и `ticketId` генерируются как **UUID версии 8**: старшие 10 бит поля `custom_a` несут номер виртуального шарда. Номер назначается сеансу при импорте его снимка и хранится в нём: обычный сеанс получает `hash(sessionId) mod 960` по стабильной хеш-функции, не зависящей от языка; горячий — свободный номер из резерва 960..1023. Формат `uuid` в контрактах не меняется, а описание `orderId` в OpenAPI запрещает клиентам разбирать его структуру. Будущая карта «виртуальный шард → узел» — версионируемая таблица в конфигурации, которую API и worker загружают с версией; сегодня все 1024 виртуальных шарда отображаются на один кластер.

## Последствия

**Что выигрываем.** Сегодня — простота одной базы: резерв, заказ и билет остаются одной локальной транзакцией, отчёты не обходят узлы, а подтверждённые данные всех четырёх баз переживают потерю любого одного узла. Завтра — шардирование без миграции идентификаторов: схема мест, резерв и статус заказа попадают в один шард, переезд идёт целыми виртуальными шардами, горячий сеанс уезжает на свой узел, не ломая маршрут по `orderId`.

**Чем платим.**
- Три узла PostgreSQL и менеджер переключения с хранилищем консенсуса; задержка каждого commit на сетевой круг до реплики.
- Пустой кворум останавливает новую запись во всех четырёх базах, включая каталог и уведомления, — тот же главный компромисс: корректность важнее доступности подтверждения.
- Одно переключение лидера съедает около 10% недельного бюджета SLI-1.
- Идентификатор перестаёт быть непрозрачным. Генерация требует номер шарда сеанса в момент создания — в команде резервирования он известен из снимка.
- 1024 виртуальных шарда — предел числа физических шардов без перевыпуска идентификаторов.
- Переключение лидера требует синхронизированных часов узлов: срок резерва проверяется по времени БД.

## Условия пересмотра

- Пик или горячие секции `booking_db` превысили порог — включить шардирование по `sessionId` через заложенные виртуальные шарды.
- Пустой кворум или переключения случаются чаще, чем позволяет бюджет SLI-1, — третья реплика в кворуме.
- Чтение каталога стало нагрузкой на лидера — анонимные GET каталога на реплику, с порогом отставания и уменьшением `s-maxage` на это отставание.
- Появилось требование пережить потерю площадки — начинать с модели согласованности между регионами, а не с добавления реплик.

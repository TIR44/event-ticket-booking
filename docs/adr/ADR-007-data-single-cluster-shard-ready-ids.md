# ADR-007: один кластер с синхронными репликами, идентификаторы покупки несут виртуальный шард

- **Статус:** принято для учебного проекта
- **Дата:** 2026-10-27
- **Драйверы:** Q-01, Q-02, Q-04

## Контекст

Быстрее всего растёт Booking: места сеансов, резервы, заказы, намерения, билеты и их ключи — около 58 млн строк и 30–40 ГБ в год по A-08. В пик A-03 это до 50 команд изменения в секунду, то есть порядка 300–500 записей строк. [Разбор по лестнице масштабирования](../data-scaling.md#шаг-2-шардировать-или-нет) показал, что один узел PostgreSQL держит это с запасом, а шарды сегодня добавили бы только издержки.

Там же нашлись две проблемы, которые от шардов не зависят. Первая: `orderId` — случайный UUID, а самое частое чтение системы — опрос статуса заказа каждые 4–6 секунд. При будущем шардировании по `sessionId` этот запрос ушёл бы во все шарды. Вторая: все четыре БД жили на одном экземпляре без копий, и [тактики надёжности](../reliability.md#тип-сбоя-и-первая-тактика) не имели ответа на потерю его диска.

| Вариант | Польза | Цена и решение |
|---|---|---|
| Шардировать Booking сейчас по `sessionId` | Готовность к росту записи | Отчёты организатора обходят все шарды, миграции и копии умножаются на число узлов, нагрузки для этого нет. Отклонено |
| Шардировать по `buyerId` | Все заказы покупателя в одном месте | Два покупателя одного места попадают в разные шарды, исключительность требует распределённой транзакции. Отклонено |
| Одна база, случайные UUID, без реплик | Минимум работы сегодня | Потеря диска теряет оплаченные покупки; переход к шардам потом требует миграции всех идентификаторов. Отклонено |
| Один кластер, синхронные реплики для строгих баз, идентификаторы с виртуальным шардом | Ноль потерь после commit для права и денег, будущие шарды без миграции идентификаторов | Больше узлов, задержка commit на сетевой круг, остановка записи строгих баз при потере обеих реплик. Выбрано |

## Решение

Четыре БД остаются **в одном кластере PostgreSQL** без шардов. Шарды возвращаются в повестку по числу: пик устойчиво выше 500 команд изменения в секунду после вертикального роста или горячие данные `booking_db` больше 500 ГБ.

Кластер — **лидер и две реплики**. Для `booking_db` и `payments_db` commit синхронный с кворумом «любая одна из двух», для `catalog_db` и `notifications_db` — локальный. Дедлайн запроса не отменяет ожидание реплики; прерванное ожидание считается неизвестным исходом. Все базы пишут и читают только лидера. Отказ лидера закрывается автоматическим переключением с ограждением старого лидера, цель — до 60 секунд. Дополнительно — базовые копии и непрерывный архив журнала для восстановления после логической ошибки.

`orderId`, `reservationId` и `ticketId` генерируются как **UUID версии 8**: старшие 10 бит поля `custom_a` несут номер виртуального шарда. Номер назначается сеансу один раз, при импорте его снимка: по умолчанию первые 10 бит SHA-256 от `sessionId`, то есть стабильная и независимая от языка функция; для заранее известного горячего сеанса — отдельный виртуальный шард из резервного диапазона. Формат `uuid` в контрактах не меняется. Будущая карта «виртуальный шард → узел» живёт в клиентской библиотеке backend-артефакта; сегодня все 1024 виртуальных шарда отображаются на один кластер.

## Последствия

**Что выигрываем.** Сегодня — простота одной базы: резерв, заказ и билет остаются одной локальной транзакцией, отчёты не обходят узлы, подтверждённые покупка и деньги переживают потерю любого одного узла. Завтра — шардирование без миграции идентификаторов: схема мест, резерв и статус заказа попадают в один шард, переезд идёт целыми виртуальными шардами, горячий сеанс уезжает на свой узел, не ломая маршрут по `orderId`.

**Чем платим.**
- Три узла PostgreSQL и менеджер переключения с хранилищем консенсуса; задержка каждого строгого commit на сетевой круг до реплики.
- Потеря обеих реплик останавливает новую запись Booking и Payments — тот же главный компромисс: корректность важнее доступности подтверждения. Каталог и уведомления продолжают работать.
- Одно переключение лидера съедает около 10% недельного бюджета SLI-1.
- Идентификатор перестаёт быть непрозрачным: клиентам и интеграциям прямо запрещено разбирать его структуру. Генерация требует `sessionId` в момент создания — в команде резервирования он есть всегда.
- 1024 виртуальных шарда — предел числа физических шардов без перевыпуска идентификаторов.
- Переключение лидера требует синхронизированных часов узлов: срок резерва проверяется по времени БД.

## Условия пересмотра

- Пик или объём `booking_db` превысили порог — включить шардирование по `sessionId` через заложенные виртуальные шарды.
- Потеря обеих реплик или переключения случаются чаще, чем позволяет бюджет SLI-1, — третья реплика в кворуме.
- Чтение каталога стало нагрузкой на лидера — анонимные GET каталога на реплику, с порогом отставания и уменьшением `s-maxage` на это отставание.
- Появилось требование пережить потерю площадки — начинать с модели согласованности между регионами, а не с добавления реплик.

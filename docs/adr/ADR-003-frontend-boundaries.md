# ADR-003: один frontend с границами FSD в общем репозитории

- **Статус:** принято для учебного проекта
- **Дата:** 2026-09-20

## Контекст

Один web-клиент обслуживает покупателя и организатора. Независимых frontend-команд и конфликтующих циклов выпуска не задано. Backend остаётся модульным монолитом с Catalog, Booking, Payments и Notifications. [Доменная модель](../domain-model.md) и [допущения](../assumptions.md) не требуют отдельных frontend-приложений по числу модулей.

Нужны понятные границы изменений и единый пользовательский путь. Особенно важны замена платёжного провайдера без изменений UI и Booking — Q-05 — и проверка владельца заказа вне зависимости от клиентского маршрута — Q-07 из [сценариев качества](../architecture-drivers.md).

## Рассмотренные варианты

| Вариант | Польза | Цена и причина выбора |
|---|---|---|
| Один frontend с папками по техническим типам | Мало начальных правил | Предметный сценарий распределён между общими компонентами, API и store; границы изменений неочевидны |
| Один frontend с FSD | Видны ответственность страницы, повторные действия и модели; можно проверять направление зависимостей | Требует договорённости о публичных API и дисциплины импортов; выбран |
| Несколько frontend в отдельных репозиториях | Независимые версии и владение | Нужны отдельные релизы и согласование контрактов; реальной организационной причины сейчас нет |
| Микрофронтенды с runtime-композицией | Возможны независимые выпуски частей | Добавляют shell/remote, совместимость зависимостей и обработку отказа remote; не оправданы одним циклом работы |

Организация репозитория и runtime-композиция — разные оси. Один репозиторий не требует микрофронтендов, а микрофронтенды сами по себе не изолируют сбой общего runtime.

## Решение

Сохранить существующий репозиторий проекта и проектировать одну frontend-сборку с одним выпуском. Документация, frontend и backend могут изменяться согласованно, но frontend и backend поставляются отдельными артефактами. Дополнительный workspace-оркестратор и общие пакеты без потребителей не вводятся.

Применить FSD в объёме [карты frontend](../frontend-architecture.md): App, Pages, при обоснованном повторном использовании Features, Entities, Shared. Не создавать Processes и пустые слои. На странице checkout координируются резерв, заказ и платёжная попытка; Entities не импортируют соседние Entities. Компонент, составляющий всю единственную страницу, не превращается в Widget только ради слоя.

Потребитель импортирует публичный API нижнего среза; глубокие импорты и обратные зависимости запрещены. Общий транспорт не содержит правил оплаты. UI использует публичный API Booking, который предоставляет связанные сведения об оплате через порт Payments; особенности провайдера остаются в backend-адаптере Payments. Эта предметная агрегация уже нужна обоим сценариям web и не требует отдельного BFF. Клиентских вариантов ответа, сложных общих политик и смены протокола пока нет; функции proxy и API, цена составного чтения и условия пересмотра описаны в [границе frontend](../frontend-architecture.md#клиенты-и-необходимость-bff). Проверка владельца заказа выполняется backend; скрытая в интерфейсе ссылка не заменяет её.

## Последствия

Положительные: один маршрут покупки и один выпуск проще согласовать; срезы показывают предметную ответственность; изменения формата провайдера локализованы. Общие решения можно проверить в одном review.

Отрицательные: frontend нельзя выпускать независимо по частям; ошибка общей оболочки способна затронуть весь UI; правила импортов требуют проверки. FSD не обеспечивает безопасность или правильность оплаты автоматически.

## Проверка и пересмотр

При реализации анализ импортов выявляет циклы, deep imports и зависимости вверх. Контрактная проверка замены провайдера подтверждает, что Booking и frontend не требуют изменений при прежних платёжных возможностях; учебная цель Q-05 — адаптер и подключение за два человеко-дня, а не измеренный результат текущей работы.

Решение пересматривается при появлении независимых команд, измеримых задержек общего выпуска либо требования изолировать отдельный runtime. Сначала определяется пользовательская граница и владение, затем выбираются репозиторий и способ композиции.

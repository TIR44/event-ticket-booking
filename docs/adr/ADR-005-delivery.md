# ADR-005: неизменяемый артефакт, проверка окружений и откат

- **Статус:** принято для учебного проекта
- **Дата:** 2026-09-20

## Контекст

Выпуск frontend может оборвать оформление заказа или загрузку старого chunk. Повторная сборка под окружение затрудняет доказательство того, что в production попала проверенная версия. Основные риски связаны с повтором оплаты Q-02, восстановлением Q-04, производительностью Q-06 и приватностью Q-07 из [сценариев качества](../architecture-drivers.md).

В репозитории пока только документация. Здесь выбирается способ будущей доставки, а не утверждается наличие работающего CI/CD.

## Рассмотренные варианты

| Вариант | Польза | Цена |
|---|---|---|
| Ручная загрузка файлов поверх production | Минимальный начальный процесс | Возможна смесь версий; непонятны состав выпуска и откат |
| Отдельная сборка под каждое окружение | Адреса и настройки зашиваются при сборке | Проверяется не тот артефакт, который затем выпускается; появляются различия зависимостей и конфигурации |
| Одна сборка и продвижение артефакта | Проверяемая идентичность версии, повторяемый откат | Нужны хранилище версий, manifest, разделение конфигурации и правила совместимости |

## Решение

Собирать frontend один раз в фиксированной среде с lockfile. Идентифицировать артефакт commit SHA и manifest. Продвигать тот же набор файлов через изолированное preview и staging в production после проверки. Конфигурация окружения отделена от кода; `/api` выбирает backend через маршрутизацию окружения, секретов в browser bundle нет.

Проверки перед выпуском покрывают типы, границы импортов, критические контракты, повтор оплаты и бюджет Q-06. Preview использует изолированные тестовые данные, sandbox оплаты и тестовый приёмник сообщений. По закрытии PR окружение и его данные удаляются; пропуски основной очистки устраняются ежедневной проверкой закрытых PR. Реальные PR и окружения в рамках подготовки ДЗ не создаются.

Сначала публикуются хешированные assets, затем переключается HTML/manifest. HTML использует `no-cache`; старые assets остаются доступны старым клиентам. Откат возвращает предыдущий manifest, а не переигрывает операции или данные backend. Контракт API сохраняет совместимость с поддерживаемыми активными frontend-клиентами.

## Последствия

Положительные: можно установить, какая версия проверена и запущена; откат не требует пересборки; секреты окружения не попадают в bundle. Регрессия конкретного выпуска сопоставляется с метриками по его версии.

Отрицательные: старые assets занимают место; нужны изоляция и очистка preview; backend вынужден поддерживать старые клиенты на время перехода. Откат UI не исправляет ошибочно проведённую денежную операцию и не откатывает БД.

## Проверка и пересмотр

При реализации проверяются идентичность артефакта между окружениями, отсутствие приватных ответов в общем кеше и работа открытой до релиза вкладки. В sandbox проверяются timeout оплаты, восстановление по `orderId`, загрузка предыдущего checkout chunk и откат без второй операции провайдера. [Pipeline и критерии приёмки](../delivery.md).

Выпуск останавливается при недоступном checkout, нарушенном контракте или превышении согласованного бюджета. Ответственный за выпуск переключает предыдущий артефакт и проверяет путь покупки. Количество успешных прогонов и процент покрытия сами по себе не заменяют проверку этих рисков.

Решение пересматривается при появлении runtime-рендеринга, независимых frontend-релизов или требований, несовместимых с общей browser-сборкой. Тогда отдельно проектируются исполнение, совместимость и откат; текущая схема не растягивается на новый режим молча.

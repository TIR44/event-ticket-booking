# ADR-004: CSR, CDN и разделение загрузки по маршрутам

- **Статус:** принято для учебного проекта
- **Дата:** 2026-09-20

## Контекст

Основной сценарий — интерактивная покупка ограниченного ресурса. Наличие места, состояние резерва и результат оплаты подтверждает сервер. Требование поискового привлечения или содержательного HTML без JavaScript пока не задано. Решение опирается на [допущения](../assumptions.md) и Q-06 — производительность frontend из [сценариев качества](../architecture-drivers.md).

## Рассмотренные варианты

| Вариант | Преимущество | Цена |
|---|---|---|
| CSR со статической доставкой | Нет отдельного сервера рендера, простая доставка интерактивного приложения | Первый экран зависит от загрузки JS и чтения API |
| SSR | Начальный HTML может прийти с содержательными данными | Серверная задержка, гидратация, стоимость исполнения и отказ рендера |
| SSG публичных страниц + CSR покупки | Публичные описания можно раздавать заранее | Нужно обновлять публикации; доступность места и покупка всё равно проверяются API |

## Решение

Начать с CSR для всех маршрутов первой версии и одного статического артефакта через CDN. `/api` того же origin направляется reverse proxy в монолит. SSR-сервис, edge-рендеринг и отдельный BFF не добавляются.

Checkout загружается отдельным route chunk, а инструменты организатора — только на соответствующем маршруте. Код checkout допускается предзагружать после выбора сеанса; это не создаёт резерв или платёж. Реквизиты карты принимает провайдер, конкретный browser SDK пока не выбран.

HTML ревалидируется через `no-cache`. Хешированные JS/CSS неизменяемы и сохраняются для старых вкладок. Публичный каталог допускает кеш до 60 секунд; отображаемая доступность — до 5 секунд только как подсказка. Заказ, резерв, платёжный статус и билет имеют `private, no-store`. Никакая копия доступности не даёт права на место; это поддерживает Q-01 и Q-07.

## Последствия

Положительные: меньше исполняемых серверных компонентов; frontend не зависит от готовности SSR; покупатель не загружает редактор организатора. Один артефакт удобно выпускать и откатывать. Условная оценка сокращения загрузки JS и её влияния на LCP/TTFB приведена в [доставке](../delivery.md#условная-оценка-эффекта); фактических замеров нет.

Отрицательные: содержательный первый экран зависит от JavaScript; прямой вход в checkout может потребовать и оболочку, и его chunk; ошибка загрузки части кода требует понятного восстановления. CSR не гарантирует соблюдение бюджета.

## Проверка и пересмотр

Первичный профиль Q-06: Android среднего класса, 4G 4 Мбит/с, RTT 150 мс, холодный кеш. Целевые бюджеты: начальный JS ≤200 KiB gzip, дополнительный checkout chunk ≤100 KiB gzip, TTFB HTML p75 ≤800 мс, LCP p75 ≤2,5 с, INP p75 ≤200 мс, CLS ≤0,1. Это проектные гипотезы; приложения и измерений сейчас нет. [Порядок проверки](../delivery.md#бюджет-производительности) разделяет lab-результат и будущий RUM.

Сравниваются холодный каталог, прямой вход в checkout и переход со страницы сеанса. Отдельно проверяется восстановление по `orderId` после ошибки загрузки chunk без новой платёжной операции.

Решение пересматривается при подтверждённой необходимости SEO/HTML без JS либо устойчивом превышении бюджета, которое не устраняется загрузкой данных и разделением кода. SSR/SSG рассматриваются для конкретного маршрута с учётом их эксплуатационной стоимости, а не как замена серверного контроля покупки.

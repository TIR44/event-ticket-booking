# Домашние задания сквозного проекта

Тема №6 — «Чек-аут / бронирование». Принятая основа проекта сохранена в main; следующие работы развивают одну систему. Подготовлены три официальных ДЗ до урока 15 включительно, с пояснениями и источниками. Упражнения между официальными сдачами включены в соответствующий этап.

| Работа | Ветка | Собственное изменение | Начать чтение |
|---|---|---|---|
| ДЗ 2, декомпозиция | `domain-decomposition` | От main: качества/сценарии, домены и данные, C4, жизненный цикл, ADR | [Декомпозиция](02-decomposition.md) |
| ДЗ 3, frontend | `frontend-architecture` | От domain-decomposition: FSD, рендеринг, доставка, три ADR | [Фронт-архитектура](03-frontend.md) |
| ДЗ 4, взаимодействие | `interaction-model` | От frontend-architecture: интеграции, два контракта, повторы, ADR, риски/SLI | [Модель взаимодействия](04-interaction.md) |

Номера здесь — порядок слотов личного кабинета; название работы и ссылка в её файле точнее разговорной нумерации преподавателя. Урок 2 про атрибуты качества сам по себе не является «ДЗ 2»: его упражнения входят в декомпозицию.

## Как устроены локальные ветки

```text
main
  └─ domain-decomposition
       └─ frontend-architecture
            └─ interaction-model
```

Каждая следующая ветка содержит предыдущую работу и добавляет свой этап. Поэтому на `interaction-model` можно читать весь проект целиком. Это линейное развитие, без параллельных несовместимых вариантов домена.

Команды только для просмотра собственного изменения:

```sh
git diff main..domain-decomposition
git diff domain-decomposition..frontend-architecture
git diff frontend-architecture..interaction-model
```

Сейчас сравнение второй или третьей ветки с main показывает и предыдущие несданные этапы. Это ожидаемо для локальной цепочки; такое сравнение ещё не является готовым отдельным PR только с текущим ДЗ.

## Как позже сдавать

Материалы урока 18 требуют отдельный PR в main с изменениями одной официальной работы: презентация стр. 31, лонгрид стр. 8. Неофициальные инкременты можно накапливать; это не означает один общий PR за все официальные задания.

Для подготовленной цепочки подходит последовательная сдача: сначала декомпозиция; после проверки и разрешённого включения её результата в main — frontend; затем взаимодействие. Перед каждым PR необходимо проверить его diff к актуальному main. Если предыдущий PR включён squash-коммитом или получил правки при проверке, следующий этап нужно перенести/перебазировать на обновлённую основу и снова проверить согласованность.

Это технический порядок для данных зависимых веток. Точный момент merge преподаватель в доступных источниках не определяет; самостоятельно сливать работу до проверки из этого не следует. Нынешняя подготовка ограничена локальными ветками и коммитами: публикация и отправка в OTUS выполняются отдельно по решению автора.

## Общая логика

Один заказ — одно место — одна попытка оплаты. Booking атомарно владеет резервом, заказом и билетом; Payments изолирует провайдера; поздний успех требует возврата. Frontend читает серверный результат и не подтверждает покупку по локальному таймеру, редиректу или кешу. Уведомление не определяет успех покупки.

Источники истины: [словарь](../../CONTEXT.md), [допущения](../assumptions.md), [качества и сценарии](../architecture-drivers.md), [жизненный цикл](../booking-lifecycle.md). При дальнейшей правке сначала меняется соответствующее правило, затем зависимые схемы и ADR.

Результат этих ДЗ — архитектурная документация и формальные контракты. Рабочего приложения, развернутых окружений и доказанных нагрузочных показателей пока нет. Следующая официальная работа по надёжности и итоговая защита остаются будущими этапами.

При локальной подготовке проверены ссылки и якоря Markdown, синтаксис и рендеринг восьми Mermaid-схем, OpenAPI 3.1.1 и JSON Schema 2020-12 с примерами корректных и отклоняемых данных. Содержательная проверка сверила владельцев данных, TTL, оплату, возврат и восстановление UI между этапами. Эти проверки относятся к документации и схемам, не к ещё не реализованному приложению.

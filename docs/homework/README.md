## Как работы попали в main

Каждое официальное ДЗ сдавалось отдельным PR, где были видны только его изменения: урок 18, презентация стр. 31, лонгрид стр. 8. Первые четыре PR открывались цепочкой с последовательными базами, после зачёта влиты в main по порядку: декомпозиция, frontend, взаимодействие, надёжность. Замечания преподавателя в каждом PR исправлены в нём же до вливания.

Итоговый проект — отдельный PR `final-project` в main: в его diff только решение по данным, итоговый документ и точечные уточнения прежних документов, которые из него следуют.

## Общая логика

Один заказ — одно место — одна попытка оплаты. Booking атомарно владеет резервом, заказом и билетом; Payments изолирует провайдера; поздний успех требует возврата. Frontend читает серверный результат и не подтверждает покупку по локальному таймеру, редиректу или кешу. Уведомление не определяет успех покупки.

Источники истины: [словарь](../../CONTEXT.md), [допущения](../assumptions.md), [качества и сценарии](../architecture-drivers.md), [жизненный цикл](../booking-lifecycle.md). При дальнейшей правке сначала меняется соответствующее правило, затем зависимые схемы и ADR.

Результат этих ДЗ — архитектурная документация и формальные контракты. Рабочего приложения, развёрнутых окружений и доказанных нагрузочных показателей пока нет. Весь проект одной страницей — в [итоговом решении](../final-solution.md).

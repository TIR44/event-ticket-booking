# План наблюдаемости покупки

План дополняет [тактики надёжности](reliability.md). Источник определений SLI, корреляции и оперативных порогов — [качество и восстановление](quality-and-operations.md); здесь они сведены в модель метрик, расчёт бюджета и эскиз дашборда. Мониторинг ещё не реализован, числа являются проектными гипотезами.

## RED для ключевого сценария

Наблюдаем путь «резерв → принятое намерение оплаты → денежный факт → решение Booking». Rate показывает поток, Errors — отказы, Duration — длительность. Синхронное принятие HTTP и окончание фонового процесса измеряются отдельно.

| Участок | Модель | Rate — что считаем | Errors — что считаем | Duration — какое время |
|---|---|---|---|---|
| Proxy → API резервирования | RED: синхронный сервис | Входные запросы/с по шаблону маршрута; дополнительно D SLI-1 | Технические плохие исходы/D: 5xx, timeout, обрыв и отказы из-за перегрузки. Штатное «место занято» — отдельный доменный исход | Две гистограммы, p50/p95/p99 в секундах: обработчик API от входа до подготовки ответа (Q-01: p95 ≤1 с на стабильном профиле); отдельно proxy от входа до ответа/прекращения ожидания, включая транспорт |
| API приёма оплаты | RED: синхронный приём | Запросы/с и отдельно новые сохранённые намерения/с | Технические ошибки; доменные отказы отдельно. Повторный 202 не считается новым намерением | p95/p99 HTTP-приёма; 202 не измеряет банк и билет |
| Worker → провайдер | Four Golden Signals: фоновая очередь, важно поймать до отказа | Попытки/с отдельно create, lookup, refund; это обращения, не уникальные платежи | Доли timeout, транспортных/серверных ошибок и ограничений квоты; достоверный отказ банка — отдельный результат | p95/p99 исходящих вызовов по операции; отдельно возраст UNKNOWN и время сверки исходной группы после восстановления |
| Payments SUCCEEDED → решение Booking | Four Golden Signals: очередь доставки | Уникальные сопоставленные переходы/с отдельно от попыток доставки | Доля не получивших решение за 5 с по SLI-2, карантин отдельно | Гистограмма t1−t0 завершённых решений, p95/p99. Число и возраст ещё незавершённых показываются рядом: перцентиль завершённых их скрывает |
| Notifications | Four Golden Signals: фоновая очередь | Попытки доставки/с | Доля временных/окончательных ошибок по классу, без содержимого сообщения | p95/p99 вызовов; возраст сохранённых заданий. Отказ доставки не меняет SLI покупки |

Каждый HTTP-запрос считается один раз на входе, а не на каждом внутреннем span. Полный длительный отказ API виден через proxy/внешние проверки даже без экспортера API. Если ответа нет, его нельзя убрать из Errors или задержек как «неизвестный ввод»; длительность незавершённых показывается возрастом до завершения/таймаута.

Насыщение (четвёртый сигнал для очередей) и ресурсы под ними по модели USE: занятые слоты/лимит, ожидание слота, число due-заданий и возраст старейшего относительно nextAttemptAt, ожидание и занятость DB-пула по роли. Host/БД: CPU, память, диск, блокировки, перезапуски и heartbeat. Это диагностика причины, а не замена пользовательских RED/SLI.

Допустимые измерения имеют ограниченный набор значений: шаблон маршрута, операция, модуль, класс результата, окружение, текущие сравниваемые версии. Для исторических версий действует ограничение хранения/агрегация. orderId, eventId, requestId, пользователь, полный URL, платёжные параметры и ключи не становятся labels. Ограниченный диагностический контекст и связи трасс через outbox описаны [отдельно](quality-and-operations.md#связь-запросов-и-фоновой-работы).

## SLI, SLO и бюджет ошибок

Используем прежние [три определения SLI](quality-and-operations.md#три-sli-и-учебные-slo), без изменения знаменателей ради красивого результата.

| SLI | Численная цель | Единица плохого исхода |
|---|---|---|
| 1. Доля технически корректных ответов резервирования N/D | ≥99,9% за скользящие 7 суток; штатный ответ «место недоступно» корректен | Запрос из D без корректного ответа. Исключаются только доказанно невалидные/неавторизованные; корректный запрос, отклонённый по перегрузке, не исключается |
| 2. Доля решений Booking не позже 5 с после committed-факта SUCCEEDED | ≥99% для семисуточной группы по t0, закрытой за 5 с до расчёта | Уникальная попытка из D без своевременного решения; подтверждение билета либо сохранённое намерение возврата завершают измерение, банковский возврат — нет |
| 3. Доля наблюдаемых первых Android-навигаций с LCP ≤2,5 с | ≥75% за скользящие 7 суток | Навигация из измеримого RUM-среза с LCP >2,5 с. Пробелы телеметрии показываются отдельно |

Для каждой доли `s = N/D`, допустимый бюджет `B = (1 − SLO) × D`, потрачено `E = D − N`, остаток `R = B − E`. `R < 0` означает превышение; отрицательное значение не скрывается. Допустимое целое число плохих исходов — `floor(B)`. Ровно нулевой остаток тоже означает исчерпание запаса. При D=0 доля и бюджет для оценки качества не определяются, а не становятся 100% и «всё хорошо».

| Учебный пример, не реальные измерения | D | N | B | E | R |
|---|---:|---:|---:|---:|---:|
| API, SLO 99,9% | 100 000 запросов | 99 960 | 100 запросов | 40 | 60 |
| Решение после SUCCEEDED, SLO 99% | 2 000 попыток | 1 985 | 20 попыток | 15 | 5 |
| RUM LCP, SLO 75% | 1 000 навигаций | 780 | 250 навигаций | 220 | 30 |

Эти бюджеты нельзя складывать: у них разные популяции и последствия. Нельзя переводить их в минуты простоя без дополнительных предпосылок о трафике. p95 резервирования ≤1 с и p95 сверки UNKNOWN ≤2 минут из Q-01/Q-04 — отдельные цели сценариев, не замена долевых SLO.

При исчерпании любого бюджета ответственный за выпуск приостанавливает обычные функциональные выпуски затронутой части. Допустимы исправление надёжности и проверяемый откат. Обработка принятых платежей, возвратов и задач продолжается. Возобновление — после устранения причины, свежих достоверных сигналов и положительного остатка в текущем скользящем окне; новый релиз не обнуляет бюджет. При малой выборке результат показывается с D, решение дополняется внешней проверкой и сценариями, а не объявляется доказанной доступностью.

Нарушение единственности денег/места или приватности имеет нулевую терпимость независимо от остатка бюджета. Недоступная телеметрия означает неизвестность: нельзя разрешить выпуск по зелёному старому графику. RUM ограничен реально полученными измерениями и не доказывает доступность у пользователей, чей JS не загрузился.

## Три основных алерта

Этот раздел — источник порогов A1–A3; [оперативная политика](quality-and-operations.md#короткие-окна-оповещений-и-диагностика) хранит те же значения и остальные специальные сигналы, при правке порогов меняются оба места. Расчёт/сбор серверных сигналов каждые 30 с; внешний наблюдатель и доставка сигнала находятся вне host PostgreSQL. «Срочно» задаёт приоритет, а не уже установленную SLA дежурства.

| Предмет и масштаб | Порог и окно | Адресат и первый шаг |
|---|---|---|
| A1. Покупатели не получают корректный ответ резервирования | Плохие исходы SLI-1 >5% за 5 минут при D ≥100; **или** 3 подряд неуспешные внешние проверки готовности `/api` с шагом 30 с. При D <100 используется вторая ветвь | Срочно, сопровождение backend: сопоставить начало с релизом и проверить proxy → API → Booking/БД; остановить продвижение неисправной версии. Проба только читает, не покупает |
| A2. Принятый денежный факт или работа не продвигается | SUCCEEDED без решения Booking старше 30 с на 2 последовательных сборах; **или** старейшее due-задание просрочено >2 минут на текущем сборе. Согласованный будущий Retry-After не является просрочкой | Срочно, сопровождение backend/worker: проверить heartbeat, аренду и обе стороны доставки; восстановить исходное задание, не создавать новую оплату. Указать модуль/класс задачи и число затронутых без личных данных |
| A3. Темп расходования бюджета SLI-1 | Две ветви, обе считаются по D своего окна, а не по остатку. **Быстрое горение:** за последний час доля плохих исходов ≥1,4% при D ≥1 000 — в 14 раз выше допустимых 0,1%; если темп и трафик сохранятся, полный 7-суточный бюджет ушёл бы за 12 часов. **Медленное горение:** за последние 6 часов доля ≥0,6% при D ≥3 000 — в 6 раз выше допустимого, полный бюджет ушёл бы примерно за 28 часов. Сроки условные: они не прогноз текущего остатка | Быстрое горение — срочно, сопровождение backend: покупка отказывает прямо сейчас, хотя A1 по 5-минутному окну этого не видит; сравнить версии и маршруты, найти долю 5xx/timeout по шаблону, при регрессии релиза откатить. Медленное горение — сообщение в чат сопровождения в рабочее время с тем же первым шагом |
| Служебный. Потеряна наблюдаемость backend/БД | Нет серверного сбора или heartbeat worker >90 с; **или** 3 подряд неуспешные проверки соединения PostgreSQL с шагом 30 с | Срочно, сопровождение backend: внешним наблюдателем проверить доступность host/API, БД и самого сбора. Показать последнюю свежую метку; не подставлять нули |

A1–A3 — три алерта на симптом покупателя: отказ резервирования сейчас, застрявшие деньги, медленная потеря надёжности. Служебный алерт на потерю наблюдаемости не считается симптомом покупателя, но без него A1–A3 могут молчать по ложной причине. Подтверждённое нарушение инварианта, денежный карантин/REVIEW_REQUIRED, длительный UNKNOWN и ошибки chunks сохраняют ранее описанные специальные реакции; они не удалены ради числа «три». Сигналы с одной причиной группируются в инцидент, повторное уведомление — при ухудшении/смене состояния. При недоступной БД A2 не вычисляется по старым данным как свежий; действует служебный алерт.

После первичного действия проверяются пользовательский исход, накопленные задачи и свежесть наблюдения; восстанавливаются прежние операции. В разборе инцидента сохраняются начало, обнаружение, действия, восстановление и причина. Если считаем MTTR, здесь это время от начала пользовательского нарушения до восстановления пользовательского сценария; время обнаружения показывается отдельно. Полный runbook и фактический график дежурств ещё не разработаны.

## Эскиз дашборда

Верхняя строка: окружение, интервал, текущая/предыдущая версия, время последнего сбора и состояние «свежие / нет данных». По умолчанию качество показывается за 7 суток, текущий сбой — за 15 минут с шагом 30 с; расчёты алертов сохраняют собственные окна. Изменение интервала просмотра не меняет SLO.

| Левая панель | Правая панель |
|---|---|
| **1. Качество и бюджет:** SLI-1/2/3, N/D, цель, B/E/R; размер и покрытие выборки RUM, ожидающие оценки новые SUCCEEDED | **2. RED API:** запросы/с, технические ошибки и доменные отказы отдельно, p50/p95/p99 API с линией Q-01 1 с; отдельно длительность proxy и входные 429/503 |
| **3. Денежный процесс:** SLI-2, p95/p99 t1−t0, возраст/число незавершённых, UNKNOWN, due backlog, карантин; отдельная исходная группа Q-04 после восстановления | **4. Внешние зависимости и ёмкость:** latency/ошибки create/lookup/refund/уведомлений, quota, занятые/ожидающие слоты по группе, пулы БД по роли |
| **5. Host и БД:** готовность API, heartbeat, свежесть сбора, CPU/память/диск, соединения, блокировки, рестарты; при отказе БД — неизвестность | **6. Frontend и релизы:** LCP по маршруту/версии/Android-срезу, доля chunk-ошибок и покрытие, аннотации выпуска/отката |

Из точки графика можно перейти к трассам/ограниченному журналу по времени и requestId; конкретные заказы не публикуются на общем дашборде. Метрики дают симптом, логи — события, трассы — путь/длительности; причину проверяют сопоставлением, а не выводят автоматически из одного графика. Отказ экспорта телеметрии не должен блокировать или терять outbox.

Это схема панелей для обсуждения и реализации, не действующий Grafana dashboard. Достаточность подтверждается покрытием [критериев ДЗ](homework/05-reliability.md); работоспособность сбора/алертов проверяется после реализации.
